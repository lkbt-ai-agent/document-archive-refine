# 용어

이 글에 나오는 핵심 용어를 먼저 한 줄로 정의한다. 더 자세한 설명은 `docs/glossary.md`에 있다.

- 토큰: 모델이 텍스트를 처리하는 최소 단위다. 단어 전체일 수도, 단어 일부나 문장부호일 수도 있다.
- 토크나이저: 글을 토큰으로 자르는 규칙과 사전이다. 무거운 모델 추론이 아니라 가벼운 규칙이다.
- 청크: 긴 문서를 검색과 임베딩에 좋게 나눈 작은 텍스트 조각이다.
- 청킹: 긴 문서를 토큰 수 기준으로 여러 청크로 나누는 과정이다. 이 프로젝트는 약 512토큰 단위로 자르고 64토큰을 겹친다.
- 트랜스포머: 토큰들 사이의 관계를 따져 각 토큰을 문맥이 반영된 벡터로 바꾸는 신경망 구조다. LLM과 임베딩 모델의 공통 뼈대다.
- 토큰별 벡터: 트랜스포머가 토큰 하나하나에 대해 내놓는 벡터다. 청크 한 개에서 토큰 수만큼 나온다.
- 풀링: 토큰별 벡터 여러 개를 하나의 문장(청크) 벡터로 합치는 방식이다. 이 프로젝트는 cls 풀링을 쓴다(`scripts/llama-embed.sh --pooling cls`).
- L2 정규화: 각 숫자를 벡터 길이로 나눠 길이를 1로 맞추는 처리다(방향은 그대로). 의미 비교에서 중요한 것은 화살표의 방향(의미)이지 길이가 아니다. 길이를 모두 1로 통일하면 방향(각도)만으로 의미를 비교할 수 있고, 이것이 코사인 유사도다. 길이가 다 1이면 그 계산이 단순한 내적으로 끝나 빠르고 일관된다.
- 임베딩: 위 과정을 모두 거쳐 한 청크의 의미를 담아 낸 하나의 숫자 벡터다. 이 프로젝트는 1024차원이며 L2 정규화된 채로 나온다.

이 용어들은 한 흐름으로 엮인다. 특히 임베딩은 한 번에 뚝딱 나오는 게 아니라 아래 여러 단계를 거친다.

1. 토크나이저가 문서를 토큰으로 자른다.
2. 청킹이 토큰 수를 세어 약 512토큰짜리 청크로 문서를 나눈다(64토큰 겹침).
3. 청크를 다시 토큰으로 바꿔 트랜스포머에 넣는다.
4. 트랜스포머가 토큰마다 문맥이 반영된 벡터를 하나씩 낸다. 이때 나온 것이 토큰별 벡터다.
5. 풀링이 그 토큰별 벡터들을 하나의 문장(청크) 벡터로 합친다. 이 프로젝트는 cls 풀링이다.
6. L2 정규화로 그 문장 벡터의 길이를 1로 맞춘다. KURE-v1은 이미 정규화된 채로 출력하므로 따로 다시 정규화하지 않는다.
7. 완성된 1024차원 벡터를 저장해 의미 검색에 쓴다.

- 즉 "청크를 임베딩한다"는 말은 위 3번부터 6번까지를 한 단어로 줄인 표현이다.
- 이 사건은 2번(청킹이 토큰 수를 세는 단계)에서 토크나이저를 줄마다 HTTP로 부른 것이 화근이다.

# Problem

- 사용자가 SH 폴더에 큰 공고 PDF 여러 개를 한꺼번에 올렸다.
- 문서들이 인제스트에서 실패로 끝났다. 화면 카드는 두 가지 모습을 보였다.
- 첫째 카드는 빨간 "실패" 점만 있고 아래 설명 문구가 없다.
- 둘째 카드는 "실패"와 함께 "인제스트가 취소 또는 타임아웃으로 중단됨"이라는 문구를 보였다.
- 워커 로그에서 같은 시간대에 인제스트 잡 5개가 실패했다.
  - `6f665c80-2971-4619-9d98-569f1f472f7c` 751.74초 후 `ConnectTimeout`
  - `e922be41-2d44-4c18-8d15-c28c6842a39c` 902.37초 후 `TimeoutError`
  - `d3cd98a8-8957-41d9-976e-82251873564b` 902.53초 후 `TimeoutError`
  - `b2e8968f-a0fa-4fd1-a462-14d58aa8f76e` 902.54초 후 `TimeoutError`
  - `dc5a5eea-419a-4f1c-8d38-1a771377e4de` 552.90초 후 `ConnectTimeout`
- 실패 시점에 llama 서버는 살아 있었다. `:8080/health`와 `:8081/health` 모두 `{"status":"ok"}`였다.

# Cause

쉽게 말하면, 문서를 잘게 나누는 "청킹" 단계가 너무 느리고 약해서 무너졌다.

### 0. 워커와 두 llama 서버의 관계

- 세 가지는 서로 다른 프로세스다. 워커가 부르는 쪽이고 두 llama 서버가 응답하는 쪽이다.
- 워커(arq)는 모델을 직접 갖지 않는다. 인제스트 작업을 실행하며 필요할 때 두 서버에 HTTP로 요청한다.
- 생성 서버(`:8080`, 설정 `llama_chat_url`)는 a.x-4.0-light 모델을 띄운다. 메타 생성과 RAG 답변 생성을 맡는다.
- 임베딩 서버(`:8081`, 설정 `llama_embed_url`)는 KURE-v1 모델을 띄운다. 청크 임베딩(`/embedding`)과 토큰 세기(`/tokenize`)를 맡는다.
- 인제스트 한 건에서 워커가 부르는 순서는 아래 그림과 같다.

```
워커(arq)  ─ 인제스트 1건 처리 ─┐
  1) PDF에서 글자 뽑기            (워커 자체, 외부 호출 없음)
  2) 메타 생성  ───── HTTP ─────▶ :8080 (생성 서버)
  3) 청킹: 토큰 세기 ─ HTTP ────▶ :8081 (임베딩 서버 /tokenize)   ← 줄마다 반복!
  4) 임베딩  ──────── HTTP ─────▶ :8081 (임베딩 서버 /embedding)
  5) DB 적재                       (워커 → PostgreSQL)
```

- 즉 워커는 손님(호출자)이고 두 서버는 가게(피호출자)다. 셋은 네트워크로 통신한다.
- 이 사건은 3번에서 워커가 `:8081`을 줄마다 수천 번 부른 것이 화근이다.

### 1. 청킹이 글자를 셀 때 줄마다 서버에 물어본다

- 청킹은 청크 크기를 토큰 수로 맞추는데, 그 수는 임베딩 모델의 진짜 토크나이저로 세야 정확하다.
- 그래서 `count_tokens`가 텍스트 한 줄마다 llama 임베딩 서버(`:8081/tokenize`)에 HTTP 요청을 보낸다(tokenizer.py:14-22).
- 더 나쁜 점은, 그 함수가 요청 한 번마다 새 `httpx.AsyncClient`를 열고 닫는다는 것이다(tokenizer.py:17). 연결을 재활용하지 않는다.
- 이번 SH 공고들은 수십 페이지짜리라 줄이 수천 개다. 그래서 서버에 수천 번을 한 줄씩 차례로 물어본다.

### 2. 느려서 타임아웃 ("취소 또는 타임아웃" 카드)

- 한 줄씩 수천 번 왕복하니 한 문서를 처리하는 데 900초가 넘었다.
- 워커에는 잡 제한 시간이 있다. `job_timeout=900`(초)이다(worker.py:21).
- 900초를 넘기면 워커가 그 잡을 강제로 끊는다. 로그의 `902.37s ! ... TimeoutError`가 이것이다.
- 끊길 때 파이썬은 `CancelledError`를 낸다. 파이프라인이 이걸 잡아 문서를 실패로 적고 "인제스트가 취소 또는 타임아웃으로 중단됨"이라고 남긴다(pipeline.py:154).
- 그래서 둘째 카드의 문구가 나온다.

### 3. 몰려서 연결 실패 ("설명 없는 실패" 카드)

- 워커는 잡을 한 번에 4개까지 돌린다. `max_jobs=4`이다(worker.py:19).
- 큰 문서 여러 개가 같이 올라와서 인제스트 4개가 동시에 같은 `:8081` 서버를 두드렸다.
- 이 서버는 토큰 세기와 임베딩을 같이 한다. 요청이 몰리자 새 연결 자체를 못 받았다.
- 그 결과 `httpx.ConnectTimeout`이 났다(chunking.py:52에서 tokenizer.py:18 호출).
- 이 예외는 오류 메시지가 비어 있다. 로그에도 `... failed, ConnectTimeout:` 뒤가 비었다.
- 파이프라인은 `str(exc)`를 문서 오류로 적는데 그게 빈 문자열이라(pipeline.py:147), 화면에는 캡션 없이 "실패" 점만 보였다.
- 그래서 첫째 카드에는 설명이 없다.

### 곁가지

- llama가 죽은 게 아니다. 동시에 큰 문서를 처리할 때 처리량이 무너진 것이다(추정). health는 정상이었다.
- 이전 사건(resolved/01)에서 같은 류의 좀비를 막으려 `job_timeout`을 300에서 900으로 올렸다. 이번엔 900초로도 부족했다. 즉 타임아웃 상향은 근본 해결이 아니었다.

# Fix

권장안 1(토크나이저 인프로세스화)을 적용해 해결했고 검증을 마쳤다. 관측성 개선(아래 5번)도 함께 적용했다. 나머지 제안은 적용하지 않았다(인프로세스화로 근본 원인이 사라져 불필요).

- (적용) 토크나이저를 워커 안에서 직접 돌린다. KURE 토크나이저를 인프로세스로 로드해 HTTP 호출 자체를 없앴다. `backend/src/ingestion/tokenizer.py`가 동봉 토크나이저(`tokenizers` 라이브러리)를 모듈에서 한 번 로드해 토큰 수를 세고, `chunking.py`는 라인을 한 번에 토큰화하는 `count_tokens_batch`를 `asyncio.to_thread`로 오프로드한다(plan 05-chunking-tokenizer-inprocess).
- (적용) 빈 오류 메시지를 막는다. `pipeline.py`가 예외 문구가 비면 예외 타입 이름을 문서 `error`에 적어 화면이 원인을 보이게 한다.
- (미적용) HTTP를 계속 쓰면, 모듈 레벨 공유 `httpx.AsyncClient` 하나를 재사용하고 여러 줄을 한 요청으로 묶어 보낸다. 인프로세스화로 `:8081/tokenize` 호출 자체가 사라져 불필요해졌다.
- (미적용) 토큰 세기를 생성 서버(`:8080`)로 보내 임베딩 서버(`:8081`)와의 경합을 푼다. 같은 이유로 불필요해졌다.
- (미적용, 임시) `job_timeout`을 더 올리거나 `max_jobs`를 줄인다. 증상만 누르는 임시 조치라 채택하지 않았다.

### 검증

- 인프로세스 토큰 수가 서버 `/tokenize` 결과와 근접함을 한국어 표본으로 확인했다(정확 일치는 불필요, 16배 여유).
- 수십 페이지 공고 PDF가 줄 단위 HTTP 왕복 없이 인제스트를 완료하며, 동시 다건 업로드에서 `:8081` 경합으로 인한 타임아웃과 `ConnectTimeout`이 사라졌다.

### 토크나이저 인프로세스화 상세 (1번 권장안)

- 인프로세스화는 토크나이저(`# 용어` 참고)를 워커 메모리에 직접 올려, 줄마다 `:8081`에 묻지 않고 워커 안에서 토큰 수를 세는 것이다(HTTP 호출 0).
- 비유하면, 단어 수를 셀 때마다 옆 사무실에 전화하던 것을 사전을 내 책상에 두고 직접 세는 것이다.

이 방안이 적합한 이유는 다음과 같다.

- 장애의 두 증상(타임아웃, 연결 실패)은 모두 줄 단위 HTTP에서 왔다. HTTP를 없애면 둘 다 사라진다.
- 토큰 수가 서버와 조금 달라도 위험하지 않다. 청크 목표는 약 512토큰인데 임베딩 서버는 8192토큰까지 받는다(약 16배 여유, `scripts/llama-embed.sh`의 `--ctx-size 8192 --ubatch-size 8192`). 따라서 토큰 수가 두세 배 어긋나도 청크가 한도를 넘지 않는다.
- 임베딩 API는 토큰이 아니라 글(text)을 받아 서버가 다시 토큰화한다(llama_client.py `embed`). 우리 토크나이저는 "어디서 자를지"만 정하고 임베딩 정확도에는 직접 관여하지 않는다.
- 따라서 토크나이저가 달라 생기는 영향은 깨짐이 아니라 청크 경계가 미세하게 달라지는 검색 품질 차이다. 이는 안전 문제가 아니라 품질 문제다.
- KURE-v1은 BAAI/bge-m3를 파인튜닝한 모델이고, 그 토크나이저 파일이 공개돼 있어 가벼운 라이브러리로 바로 로드할 수 있다.

사이드이펙트는 아래와 같다. 처음 보는 사람을 위해 풀어 쓴다.

- 새 라이브러리 추가. 토크나이저를 읽으려면 라이브러리가 하나 더 필요하다. 무거운 `transformers` 대신 가벼운 `tokenizers`면 충분하다. 이미 OCR 같은 큰 라이브러리가 들어 있어 부담은 작다.
- 토크나이저 파일 동봉. 토크나이저는 사전 파일이 있어야 동작한다. 처음 실행할 때 인터넷에서 받아오게 두면 망 없는 환경에서 멈출 수 있다. 그래서 사전 파일을 리포에 같이 넣어 두는 게 안전하다. 이 앱은 모델을 로컬 파일로 쓰는 오프라인 지향이다.
- 특수 토큰 차이. 토크나이저는 문장 앞뒤에 보이지 않는 표식 토큰을 자동으로 붙일 수 있다. 그러면 줄마다 토큰 수가 한두 개 더 세진다. 512 목표에 비해 무시할 양이지만, 정확히 맞추려면 그 자동 표식을 끄는 옵션을 준다(`add_special_tokens=False`).
- 동기 처리 주의. 지금 토큰 세기 함수는 결과를 기다리는 async 방식이다. 직접 세기는 곧바로 계산하는 동기 방식이라, 줄마다 부르면 잠깐씩 다른 작업을 막을 수 있다. 한 번 계산이 매우 짧아 실무 영향은 작지만, 토크나이저는 한 번만 메모리에 올려 재사용하고 가능하면 글 전체를 한 번에 세는 게 좋다.
- 메모리 약간 증가. 사전이 워커 메모리를 몇 메가바이트 차지한다. 한 번만 올리고, 모델 본체는 워커가 아니라 별도 서버에 있으므로 부담은 거의 없다.
- 기존 청크와 경계 차이. 이미 올린 문서는 서버 토크나이저로 잘렸고, 앞으로 올릴 문서는 직접 세기로 조금 다르게 잘릴 수 있다. 검색은 계속 되며 깨지지 않는다. 다시 인제스트하면 어차피 같은 기준으로 다시 잘린다.

구현 메모.

- KURE-v1(bge-m3 계열) 토크나이저를 `tokenizers`로 한 번 로드해 재사용한다(제안).
- 토큰 수를 셀 때 자동 표식을 끈다(`add_special_tokens=False`).
- gguf 양자화 모델의 서버 토큰화와 완전히 같은지는 검증이 필요하다(미검증). 다만 위 16배 여유 때문에 영향은 작다.

# Prevention

- 인제스트 단계 안에서 한 항목당 외부 HTTP를 줄 단위로 반복 호출하지 않는다. 호출은 묶거나 인프로세스로 처리한다.
- 외부 HTTP 클라이언트는 요청마다 새로 만들지 않는다. 공유 클라이언트로 연결을 재사용한다.
- 잡 제한 시간 상향은 임시 조치로만 본다. 느림의 원인을 먼저 없앤다.
- 오류를 문서에 적을 때 메시지가 빌 수 있다고 가정한다. 비면 예외 타입으로 대체해 화면에서 원인이 사라지지 않게 한다.
- 큰 문서 여러 개를 한꺼번에 넣기 전에 소량으로 한도를 확인한다(resolved/01과 같은 맥락).
