# Problem

쉽게 말하면, "올해" 같은 상대 시점이 붙은 RAG 질문이 전부 "찾을 수 없습니다"로 실패했다. 같은 질문에서 시간 표현만 빼면 정상으로 답했다.

- 검색 평가에서 F3(시간 필터) 시간 케이스 3건이 전부 실패했다.
  - `F3-daejeon-time-001` "올해 대전 행복주택 있었어?"
  - `F3-loan-time-001` "올해 소상공인 정책자금 융자 있어?"
  - `F3-happy-time-001` "올해 울산 행복주택 있었어?"
- 세 건 모두 rag가 인용 0건으로 거부했다(답변 "찾을 수 없습니다.").
- 시간 표현 없는 쌍(`F3-daejeon-plain-001` "대전 행복주택 알려줘" 등)은 통과했다.
- 정답 문서는 코퍼스에 있고 적재도 됐다. 시간 표현 유무만 다른데 결과가 갈렸다.
- 이 결함은 키워드 케이스 표현을 고친 뒤의 최근 run(`20260705T165354`)에서도 그대로 남았다. rag 쪽 문제라 키워드 수정과 무관하며, 전체 실패 7건 중 시간 케이스 3건이 여기에 해당한다.

# Cause

원인은 쿼리 재작성 LLM이 상대 시점 "올해"를 엉뚱한 절대 연도 "2023년"으로 바꿔 버린 것이다. 그 결과 두 경로가 동시에 깨진다.

### 먼저 흐름

- rag는 검색 전에 질의 해석을 한다. `_parse_query`가 LLM으로 `rewritten_query`, `keywords`, `time_ref`를 뽑는다(`src/search/service.py`).
- `_retrieve`는 `rewritten_query`를 임베딩해 의미 검색에 쓰고, `time_ref`를 `resolve_time`으로 절대 기간으로 바꿔 날짜 필터로 건다.
- `resolve_time`은 "올해/작년/지난달"과 4자리 연도만 해석한다(`src/search/dates.py`). 4자리 연도는 `(\d+)\s*년` 규칙이 잡아 그 연도 범위로 필터한다.

### 실측 증거: 재작성이 "올해"를 "2023년"으로 만든다

`_parse_query`를 직접 호출한 결과다.

- "올해 대전 행복주택 있었어?" 에서 `rewritten_query='2023년 대전 행복주택 공급 여부'`, `time_ref='2023년'`.
- "올해 소상공인 정책자금 융자 있어?" 에서 `rewritten_query='2023년 소상공인 정책자금 융자 여부'`, `time_ref='2023년'`.
- "올해 울산 행복주택 있었어?" 에서 `rewritten_query='2023년 울산 행복주택'`, `time_ref='2023년'`.

시스템 프롬프트는 "올해" 같은 표현을 그대로 뽑으라고 지시하지만, 생성 모델(a.x-4.0-light)이 학습 시점의 "현재"를 2023년 부근으로 기억해 상대 시점을 임의로 절대화한 것으로 보인다(추정).

### 두 경로가 함께 깨진다

- 텍스트 오염: `rewritten_query`에 "2023년"이 박혀 임베딩이 엉뚱한 연도로 쏠린다.
- 날짜 필터 오배제: `time_ref='2023년'`이 `resolve_time`을 통해 2023년 범위 필터가 된다. 평가 적재 문서 228건은 모두 `created_at`이 2026-07-02라 2023 필터에 전부 걸러진다. 후보가 0건이 되어 rag가 거부한다.
- 두 경로 중 날짜 필터만으로도 후보가 0이 되므로 실패는 확정적이다.

### ablation 확증

같은 케이스를 재작성 토글만 꺼서(`query_rewrite=False`) 다시 돌렸다. 재작성을 끄면 파싱을 통째로 건너뛰어 오염된 텍스트와 잘못된 날짜 필터가 함께 사라진다.

- F3 시간 3건이 전부 fail에서 pass로 뒤집혔다.
- 실패 유형 F3 통과율 0.40에서 1.00으로 올랐다.
- 인용율 0.833에서 1.00, 인용 정확율 0.778에서 0.944, 전체 통과율 0.851에서 0.896으로 올랐다.
- run 아티팩트: `backend/eval/runs/20260705T155025-2022d1a`(`baseline.json` 대 `no_rewrite.json`).

재작성을 끄면 낫는다는 것이 곧 재작성이 원인이라는 증거다. 다만 재작성은 동의어와 의역에도 쓰이므로 통째로 끄는 것은 해법이 아니다.

# Fix

권장안을 적용했다(plan 15-rag-relative-date-fix). 상태는 resolved다.

적용: 상대 날짜 환산을 LLM에서 떼어 정규식과 코드로 옮겼다.

- 원문 질의에서 기간 표현을 `dates.py`의 `extract_time_ref`(정규식)로 뽑는다. 대상은 `resolve_time`이 아는 고정 어휘다(올해, 작년, 재작년, 지난달, 이번달, 최근 N일, 4자리 연도).
- 뽑은 표현을 `resolve_time`에 넘겨 요청 시각 기준 실제 날짜 범위로 환산한다. LLM은 날짜를 건드리지 않는다.
- 뽑은 표현을 제거한 잔여 질의만 재작성과 임베딩 입력으로 쓴다. `rewritten_query`와 임베딩에 연도 토큰이 섞이지 않는다.
- `QueryParse`의 `time_ref` 필드와 `_PARSE_SYSTEM`의 기간 추출 지시를 없앴다. 재작성 프롬프트에는 원문에 없는 날짜를 만들지 말라는 지시를 넣었다.
- 부수로 `resolve_time`이 재작년을 작년으로 오판하던 순서 버그를 고쳤다(재작년을 먼저 검사).

검증: run `20260707T012550`에서 F3 시간 3건이 FIXED로 바뀌고 회귀는 없었다(F3 통과율 0.4에서 1.0, 인용 정확율 0.78에서 0.94).

남은 과제(제안, 미적용): `resolve_time`이 만든 연도가 요청 시각 기준으로 비상식적이면 필터를 걸지 않고 로그를 남기는 방어는 넣지 않았다.

# Prevention

- 상대날짜의 절대화는 결정적 코드(`resolve_time`)에만 맡긴다. LLM이 "올해"를 특정 연도로 바꾸게 두지 않는다.
- LLM 재작성 출력이 원문에 없는 토큰(연도)을 만들면 임베딩과 필터를 함께 오염한다. 재작성은 축약과 정규화로만 제한하고 새 사실을 넣지 못하게 한다.
- 평가 케이스에 시간 표현 유무만 다른 최소쌍(`-time` 대 `-plain`)을 둔다. 이 쌍이 이 결함을 바로 드러냈다.
- 날짜 필터가 후보를 0으로 만들면 거부가 정상 동작으로 위장된다. rag 거부를 볼 때 필터가 후보를 비운 것인지 먼저 확인한다.
