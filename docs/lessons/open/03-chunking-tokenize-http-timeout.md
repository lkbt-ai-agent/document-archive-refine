# Problem

- 사용자가 SH 폴더에 큰 공고 PDF 여러 개를 한꺼번에 올렸다.
- 문서들이 인제스트에서 실패로 끝났다. 화면 카드는 두 가지 모습을 보였다.
- 첫째 카드는 빨간 "실패" 점만 있고 아래 설명 문구가 없다.
- 둘째 카드는 "실패"와 함께 "인제스트가 취소 또는 타임아웃으로 중단됨"이라는 문구를 보였다.
- 워커 로그에서 같은 시간대에 인제스트 잡 5개가 실패했다.
  - `6f665c80-2971-4619-9d98-569f1f472f7c` 751.74초 후 `ConnectTimeout`
  - `e922be41-2d44-4c18-8d15-c28c6842a39c` 902.37초 후 `TimeoutError`
  - `d3cd98a8-8957-41d9-976e-82251873564b` 902.53초 후 `TimeoutError`
  - `b2e8968f-a0fa-4fd1-a462-14d58aa8f76e` 902.54초 후 `TimeoutError`
  - `dc5a5eea-419a-4f1c-8d38-1a771377e4de` 552.90초 후 `ConnectTimeout`
- 실패 시점에 llama 서버는 살아 있었다. `:8080/health`와 `:8081/health` 모두 `{"status":"ok"}`였다.

# Cause

쉽게 말하면, 문서를 잘게 나누는 "청킹" 단계가 너무 느리고 약해서 무너졌다.

### 0. 워커와 두 llama 서버의 관계

- 세 가지는 서로 다른 프로세스다. 워커가 부르는 쪽이고 두 llama 서버가 응답하는 쪽이다.
- 워커(arq)는 모델을 직접 갖지 않는다. 인제스트 작업을 실행하며 필요할 때 두 서버에 HTTP로 요청한다.
- 생성 서버(`:8080`, 설정 `llama_chat_url`)는 a.x-4.0-light 모델을 띄운다. 메타 생성과 RAG 답변 생성을 맡는다.
- 임베딩 서버(`:8081`, 설정 `llama_embed_url`)는 KURE-v1 모델을 띄운다. 청크 임베딩(`/embedding`)과 토큰 세기(`/tokenize`)를 맡는다.
- 인제스트 한 건에서 워커가 부르는 순서는 아래 그림과 같다.

```
워커(arq)  ─ 인제스트 1건 처리 ─┐
  1) PDF에서 글자 뽑기            (워커 자체, 외부 호출 없음)
  2) 메타 생성  ───── HTTP ─────▶ :8080 (생성 서버)
  3) 청킹: 토큰 세기 ─ HTTP ────▶ :8081 (임베딩 서버 /tokenize)   ← 줄마다 반복!
  4) 임베딩  ──────── HTTP ─────▶ :8081 (임베딩 서버 /embedding)
  5) DB 적재                       (워커 → PostgreSQL)
```

- 즉 워커는 손님(호출자)이고 두 서버는 가게(피호출자)다. 셋은 네트워크로 통신한다.
- 이 사건은 3번에서 워커가 `:8081`을 줄마다 수천 번 부른 것이 화근이다.

### 1. 청킹이 글자를 셀 때 줄마다 서버에 물어본다

- 청킹은 글을 약 512토큰 덩어리로 나눈다. 토큰 수는 임베딩 모델의 진짜 토크나이저로 세야 정확하다.
- 그래서 `count_tokens`가 텍스트 한 줄마다 llama 임베딩 서버(`:8081/tokenize`)에 HTTP 요청을 보낸다(tokenizer.py:14-22).
- 더 나쁜 점은, 그 함수가 요청 한 번마다 새 `httpx.AsyncClient`를 열고 닫는다는 것이다(tokenizer.py:17). 연결을 재활용하지 않는다.
- 이번 SH 공고들은 수십 페이지짜리라 줄이 수천 개다. 그래서 서버에 수천 번을 한 줄씩 차례로 물어본다.

### 2. 느려서 타임아웃 ("취소 또는 타임아웃" 카드)

- 한 줄씩 수천 번 왕복하니 한 문서를 처리하는 데 900초가 넘었다.
- 워커에는 잡 제한 시간이 있다. `job_timeout=900`(초)이다(worker.py:21).
- 900초를 넘기면 워커가 그 잡을 강제로 끊는다. 로그의 `902.37s ! ... TimeoutError`가 이것이다.
- 끊길 때 파이썬은 `CancelledError`를 낸다. 파이프라인이 이걸 잡아 문서를 실패로 적고 "인제스트가 취소 또는 타임아웃으로 중단됨"이라고 남긴다(pipeline.py:154).
- 그래서 둘째 카드의 문구가 나온다.

### 3. 몰려서 연결 실패 ("설명 없는 실패" 카드)

- 워커는 잡을 한 번에 4개까지 돌린다. `max_jobs=4`이다(worker.py:19).
- 큰 문서 여러 개가 같이 올라와서 인제스트 4개가 동시에 같은 `:8081` 서버를 두드렸다.
- 이 서버는 토큰 세기와 임베딩을 같이 한다. 요청이 몰리자 새 연결 자체를 못 받았다.
- 그 결과 `httpx.ConnectTimeout`이 났다(chunking.py:52에서 tokenizer.py:18 호출).
- 이 예외는 오류 메시지가 비어 있다. 로그에도 `... failed, ConnectTimeout:` 뒤가 비었다.
- 파이프라인은 `str(exc)`를 문서 오류로 적는데 그게 빈 문자열이라(pipeline.py:147), 화면에는 캡션 없이 "실패" 점만 보였다.
- 그래서 첫째 카드에는 설명이 없다.

### 곁가지

- 이 두 증상(타임아웃, 연결 실패)은 원인이 같다. 청킹의 줄 단위 토큰 세기가 너무 느리고 동시 부하에 약하다는 점이다.
- llama가 죽은 게 아니다. 동시에 큰 문서를 처리할 때 처리량이 무너진 것이다(추정). health는 정상이었다.
- 이전 사건(resolved/01)에서 같은 류의 좀비를 막으려 `job_timeout`을 300에서 900으로 올렸다. 이번엔 900초로도 부족했다. 즉 타임아웃 상향은 근본 해결이 아니었다.

# Fix

아직 고치지 않았다. 아래는 후보이며 효과가 큰 순서다. 어느 것도 적용하지 않았다.

- (제안) 토크나이저를 워커 안에서 직접 돌린다. KURE 토크나이저를 인프로세스로 로드해 HTTP 호출 자체를 없앤다. 가장 근본적이다.
- (제안) HTTP를 계속 쓰면, 모듈 레벨 공유 `httpx.AsyncClient` 하나를 재사용하고, 여러 줄을 한 요청으로 묶어 보낸다. 왕복 횟수를 크게 줄인다.
- (제안) 토큰 세기를 생성 서버(`:8080`)로 보내 임베딩 서버(`:8081`)와의 경합을 푼다.
- (제안, 임시) `job_timeout`을 더 올리거나 `max_jobs`를 줄인다. 증상만 누른다.
- (제안) 빈 오류 메시지를 막는다. 오류 문구가 비면 예외 타입 이름이라도 문서 `error`에 적어 화면이 원인을 보이게 한다.

### 토크나이저 인프로세스화 상세 (1번 제안)

- 토큰 세기는 무거운 모델 추론이 아니다. 글을 토큰 단위로 자르는 규칙과 사전만 있으면 된다.
- 지금은 그 가벼운 일을 위해 워커가 `:8081` 서버에 HTTP로 물어본다. 줄마다 왕복이 든다.
- 인프로세스화는 그 토크나이저(자르는 규칙과 사전)를 워커 프로세스 메모리에 직접 로드하는 것이다.
- 그러면 워커가 네트워크 없이 자기 안의 함수 호출로 토큰 수를 센다. HTTP 호출이 0이 된다.
- 비유하면, 단어 수를 셀 때마다 옆 사무실(`:8081`)에 전화하던 것을 사전을 내 책상(워커)에 두고 직접 세는 것이다.
- 효과는 두 가지다. 수천 번의 왕복이 사라져 즉시 계산된다. `:8081` 연결 경합이 사라져 ConnectTimeout이 없어진다.
- 주의가 하나 있다. 워커가 쓰는 토크나이저는 임베딩 서버(`:8081`)의 KURE-v1이 쓰는 토크나이저와 같아야 한다. 토큰 수가 어긋나면 청크 크기가 틀어진다.
- 구현은 KURE-v1의 토크나이저를 HuggingFace tokenizers로 로드해 쓰는 방안이 후보다(제안). gguf 양자화 모델과 토큰화가 일치하는지 검증이 필요하다(미검증).

# Prevention

- 인제스트 단계 안에서 한 항목당 외부 HTTP를 줄 단위로 반복 호출하지 않는다. 호출은 묶거나 인프로세스로 처리한다.
- 외부 HTTP 클라이언트는 요청마다 새로 만들지 않는다. 공유 클라이언트로 연결을 재사용한다.
- 잡 제한 시간 상향은 임시 조치로만 본다. 느림의 원인을 먼저 없앤다.
- 오류를 문서에 적을 때 메시지가 빌 수 있다고 가정한다. 비면 예외 타입으로 대체해 화면에서 원인이 사라지지 않게 한다.
- 큰 문서 여러 개를 한꺼번에 넣기 전에 소량으로 한도를 확인한다(resolved/01과 같은 맥락).
