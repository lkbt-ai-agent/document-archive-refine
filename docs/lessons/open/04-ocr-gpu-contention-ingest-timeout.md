# Problem

- 사용자가 SH 폴더에 큰 스캔 공고 PDF를 여러 건 올렸다(일부는 35쪽).
- 워커가 `max_jobs=4`로 4건을 동시에 처리했다.
- 같은 배치의 문서 중 3건이 ready, 3건이 실패로 끝났다.
  - ready: `d442e9d6`(7쪽, 407초), `0e0c0108`(23쪽, 810초), `5294cfa1`(20쪽, 32.7초, 이전 세션).
  - failed: `b883f408`, `94909544`(20쪽), `1ac187fd`(35쪽). 모두 약 918초 후 `TimeoutError`.
- 실패 카드 문구는 "인제스트가 취소 또는 타임아웃으로 중단됨"이었다.
- 메모리는 부족하지 않았다. 맥 미니 24GB에서 유휴 시 84%가 비어 있었다.

# Cause

원인은 메모리가 아니라 연산 자원 경합이다. OCR은 CPU를 많이 쓰고, 두 llama 서버는 단일 Metal GPU를 공유한다. 4건 동시 처리가 이 둘을 포화시켜 각 잡의 실행 시간이 900초 잡 타임아웃을 넘겼다.

### 0. 타임아웃이 세는 범위

- `job_timeout=900`은 잡 실행 전체(추출, 메타, 청킹, 임베딩)를 처음부터 잰다(worker.py:21). 청킹부터가 아니다.
- 큐 대기 시간은 세지 않는다. 슬롯이 차서 기다린 시간은 900초에 들어가지 않는다.

### 1. OCR이 CPU를 포화시킨다 (실패 1건)

- `b883f408`은 pages=None으로 끝났다. 추출조차 끝내지 못했다.
- 트레이스백 최종 프레임은 `pipeline.py:40`의 `_extract`가 부른 `extract_pdf`다(OCR 포함).
- PaddleOCR는 `asyncio.to_thread`로 워커 안에서 CPU로 돈다. 4건이 동시에 OCR을 돌려 코어를 나눠 쓰자 각 OCR이 느려졌다.

### 2. 단일 GPU를 생성과 임베딩이 공유한다 (실패 2건)

- `94909544`(20쪽)과 `1ac187fd`(35쪽)은 pages가 잡혔다. 추출과 청킹을 통과했다.
- 트레이스백 최종 프레임은 `pipeline.py:123`의 `_embed_all`이 부른 `llama_client.py:77`의 `embed`다(임베딩 서버 `:8081` 호출).
- 임베딩 서버는 슬롯 1개다(`llama-embed.sh`에 `--parallel` 없음). 생성 서버(`--parallel 4`)와 같은 Metal GPU를 공유한다.
- 추출이 시간 대부분을 먹은 뒤 임베딩 단계에서 누적 900초를 넘겼다. 임베딩 자체가 900초 걸린 게 아니라, 추출부터 쌓인 총합이 거기서 한계를 쳤다.

### 3. 동시성 한도가 자원에 맞지 않는다

- 워커 `max_jobs=4`, 생성 슬롯 4, 임베딩 슬롯 1이다(system-overview §6).
- 큰 스캔본 4건이 동시에 CPU(OCR)와 단일 GPU(생성과 임베딩)를 두고 경합했다.
- 23쪽은 4-way 경합에서도 810초로 겨우 완주했고, 35쪽은 900초를 넘겼다. 경합이 임계 지점에 있었다는 신호다.

### 곁가지

- 이번 실패는 lesson 03(청킹 토크나이저)과 무관하다. 청킹과 `count_tokens` 단계의 실패는 0건이다. 그 수정 덕분에 병목이 추출과 임베딩으로 이동했다.
- 메모리는 병목이 아니다(추정). 임베딩 모델은 634MB로 가볍고 유휴 시 84%가 비어 있었다.
- `b883f408`이 단순 경합인지 그 PDF 자체가 비정상인지는 미확인이다. 재시도로 가린다.

# Fix

아직 고치지 않았다. 후보는 효과와 안전 순이다. 어느 것도 적용하지 않았다.

- (제안) 워커 `max_jobs`를 2로 낮춘다. 동시 OCR과 임베딩 경합을 줄여 각 잡의 실행 시간을 줄인다. 큐 대기는 늘지만 `job_timeout`은 실행만 세므로 타임아웃에는 무해하다.
- (제안) `job_timeout`을 900에서 1800으로 올린다. 2-way로도 빠듯할 초대형 단건을 흡수한다. 임시책이다.
- (제안) 임베딩 서버에 슬롯을 준다. `llama-embed.sh`에 `--parallel 2~4`를 주고, 청크가 512토큰 이하라 `--ctx-size 4096 --ubatch-size 2048`로 줄여도 된다. 단 단일 GPU 공유라 처리량 증가는 제한적이다.
- (제안) OCR을 가속한다. 페이지 병렬화, 해상도 조정, 엔진 교체 등. 별도 과제다.
- 불변식을 지킨다. `max_jobs`는 생성 슬롯 수 이하로 둔다(lesson 01). 2는 4 이하라 유지된다.

# Prevention

- 인제스트 동시성(`max_jobs`)은 가장 무거운 단계(OCR과 임베딩)의 실효 처리량에 맞춘다. 생성 슬롯만 보고 정하지 않는다.
- 단일 GPU와 CPU를 공유하는 워크로드는 동시 잡 수를 보수적으로 잡는다. 처리량보다 완주율을 우선한다.
- `job_timeout`은 가장 느린 단계(대형 스캔본 OCR)를 덮을 만큼 둔다. 타임아웃은 추출부터 누적된다는 점을 기억한다.
- 대형 스캔본을 한꺼번에 많이 넣기 전에 소량으로 처리 시간을 측정한다(lesson 01과 같은 맥락).
