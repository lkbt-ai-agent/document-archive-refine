# 검색 & RAG

## 1. 기능 요구사항

- 키워드 검색 / 의미 검색 / RAG 질의응답.
- 키워드는 PGroonga, 의미는 pgvector 확장에 의존한다. 대표 시나리오: "작년 내 연봉이 얼마였지?".

## 2. 검색 종류

- 키워드/의미/RAG는 검색 UI의 단일 진입(모드 선택)에서 고른다(기본값 의미). 진입은 같고 출력만 갈린다: 키워드/의미는 결과 리스트, RAG는 답변을 반환한다.
- 키워드 검색 (희소 검색, sparse retrieval)
  - 희소 검색: 텍스트를 어휘 크기의 희소 벡터(대부분 0이고 등장 토큰 자리에만 값)로 보고 토큰을 글자 그대로 매칭한다. 정확한 단어·이름·코드에 강하지만 동의어·의역은 못 잡는다.
  - 대상: 청크 본문(`document_chunks.content`), 청크 단위.
  - 청크 텍스트를 한국어 키워드(n-gram 토큰)로 매칭하고, 매칭 청크와 그 소속 문서를 리스트로 반환한다.
- 의미 검색 (밀집 검색, dense retrieval)
  - 밀집 검색: 텍스트를 의미를 담은 밀집 벡터(임베딩)로 바꿔 벡터 유사도로 매칭한다. 동의어·의역·문맥에 강하지만 드문 정확어는 놓칠 수 있다.
  - 대상: 청크(`document_chunks`), 청크 단위.
  - 질문을 임베딩해 청크 코사인 유사도로 상위 k개를 매칭하고, 매칭 청크와 그 소속 문서를 리스트로 반환한다.
- RAG
  - 검색 단계는 의미 검색(청크)만 사용한다.
  - 검색된 청크로 컨텍스트를 만들어 답변+출처를 생성한다.

## 3. 자연어 질의 해석

- 검색 종류는 자동 분류하지 않는다. 사용자가 단일 검색 진입에서 모드(키워드/의미/RAG)를 직접 고른다(기본 의미).
- 이 단계는 타입을 고르는 게 아니라, 입력 질의에서 재작성 질의·키워드·기간·폴더를 구조화해 추출한다.
- 상대적 날짜("작년" 등)는 요청 시각을 기준으로 절대 범위로 환산한다.
- "내", "나" 등의 단어는 항상 소유자 스코프로 강제한다.

## 4. 검색·RAG 흐름

- 종류마다 시작과 끝이 다르다.
- 키워드 검색
  1. 질의 입력(사용자 키워드)
  2. 청크 본문(`document_chunks.content`) 키워드 매칭
  3. 매칭 청크·소속 문서 리스트 반환 (끝)
- 의미 검색
  1. 질의 입력
  2. 질문 임베딩
  3. 청크(`document_chunks`) 코사인 유사도 검색
  4. 상위 k개 청크·소속 문서 리스트 반환 (끝)
- RAG
  1. 자연어 질문 입력
  2. 질의 해석(§3)으로 재작성·필터 추출
     - 재작성은 원 질문에서 상대표현·군더더기를 걷어낸 핵심 질의다. 이 질의를 임베딩해 의미 검색 벡터로 쓴다(무엇을 찾을지). 필터가 아니라 검색의 의미 축이다.
     - 필터는 후보 청크 행 자체를 좁히는 조건이다(어디서 찾을지). owner 스코프는 항상 걸고, 기간은 time_ref를 요청 시각 기준 절대 범위로 환산해 걸며, 폴더는 사용자가 고른 folder_id로 건다.
     - 필터가 후보 모수를 좁히고, 재작성 벡터가 그 안에서 순위를 매긴다.
  3. 의미 검색으로 상위 k개 후보 청크 확보
  4. 컨텍스트 조립(청크 본문 + 제목·날짜·폴더·청크 식별자, 인용 번호↔청크 매핑 저장)
     - 로컬 작업이고 답변 생성 호출은 없다. 후보 청크를 `[1]`, `[2]` 번호로 이어 붙여 다음 단계의 입력을 만든다.
     - 토큰 예산을 넘지 않게 청크를 담는다(search-backend §5).
  5. 인용 강제 생성
     - 이 단계에서 LLM에 답변 프롬프트를 보낸다(전체 흐름에서 답변용 호출은 여기 한 번).
     - 시스템 프롬프트가 컨텍스트에만 근거하고 문장마다 `[n]`을 달도록 지시한다(별도 단계가 아니라 이 생성 호출의 제약, §6).
     - 스트리밍은 같은 시점에 토큰을 흘려보내 첫 토큰까지 시간을 줄인다(search-backend §5).
  6. 답변+출처 반환 (끝)
     - 로컬 후처리다. 답변의 `[n]`을 1부터 다시 매기고 인용에 청크 식별자와 근거 본문을 붙여 반환한다.

## 5. 리랭킹 (MVP 제외)

- MVP 에서는 고려하지 않는다.
- 상위 결과를 재정렬해 정밀도를 높인다.

## 6. 인용·환각 억제

- 시스템 규칙: 제공된 문서에만 근거하고, 없으면 "찾을 수 없습니다"로 답한다.
- 문장마다 인용 번호를 강제한다.
- 주입 순서: 시스템 규칙 → 컨텍스트 → 질문(마지막).

## 7. 검색 평가 게이트

- 한국어 골든셋(쿼리→정답 문서)으로 Recall@5/@20을 측정한다.
- MVP: 키워드·의미 검색별 Recall을 비교하고, RAG 답변의 인용 존재를 이진 체크한다.
- MVP 이후: 리랭크(§5) 도입 시 비교 항목에 추가한다.
- CI(지속적 통합, Continuous Integration) 파이프라인에서 결정적으로 돌린다.

## 8. 도메인 규칙

- 모든 검색·질의는 소유자 스코프를 강제한다.
- 검색 UI 에서 검색 모드를 선택할 수 있어야 한다.
- 키워드/의미/RAG는 단일 검색 진입에서 고르며, 출력만 갈린다: 키워드/의미는 결과 리스트(retrieval), RAG는 답변 생성.

## 9. 점수(score) 의미

- 키워드 검색과 의미 검색 모두 결과에 `score`를 붙이지만 뜻이 다르다.
- 키워드 score는 매칭 강도다. 질의어가 청크에 얼마나 비중 있게 등장하는지를 빈도 기반(BM25 계열)으로 재는 랭킹 값이며 유사도가 아니다.
- 의미 score는 질문 임베딩과 청크 임베딩 사이의 코사인 유사도다.
- 매칭 자체는 둘 다 일치 여부로 후보를 거르고, score는 거른 결과의 순위를 매기는 데만 쓴다.
- 두 score는 계산 방식과 값 범위가 달라 모드 사이에서 서로 비교하지 않는다. 각 모드 안의 정렬에만 쓴다.
