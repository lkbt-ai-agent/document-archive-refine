> 재시도는 문서를 읽어 검색 가능하게 만드는 과정(인제스트)이 실패했을 때, 사용자가 버튼 한 번으로 처음부터 다시 시도하게 하는 기능이다.
> 이 plan은 가장 단순한 형태(MVP)만 다룬다. 실패했고 원본 파일이 남아 있는 문서를 통째로 다시 처리한다. 근거는 research 08(§6.1 레벨 1, §6.2 레벨 2 일부, §7).
> 두 가지를 먼저 알아야 한다. 같은 작업을 약 1시간 동안 다시 큐에 못 넣는 arq 차단이 있어 먼저 풀어야 한다(research 08 §4.2). 원본 파일이 없으면 다시 처리할 수 없고 재업로드를 안내해야 한다(research 08 §3).

## 준비 정리 (선행)
- [ ] A1 아키텍처 `ingestion-backend §1`의 지수 백오프 재시도 서술을 실제 동작(자동 재시도 없음)에 맞게 고친다 (research 08 §4.3).
- [ ] A2 타임아웃 경로가 문서를 failed로 종결하면서도 arq가 재실행하는 불일치를 정리한다 (research 08 §4.3).

## 백엔드 재시도
- [ ] B1 `documents`에 시도 횟수 컬럼(`retry_count`)을 추가하는 마이그레이션을 만든다 (재시도 상한용, research 08 §6.1).
- [ ] B2 재시도 서비스 메서드를 만들어 `status=failed`이고 MinIO 객체가 있으면 `status=processing`으로 되돌리고 인제스트를 다시 enqueue한다 (research 08 §6.1).
- [ ] B3 재투입 전에 arq 결과 키를 지우거나 시도별 `_job_id`(`ingest:{id}:{n}`)를 써서 1시간 차단을 푼다 (research 08 §4.2).
- [ ] B4 객체가 없으면 재인제스트 대신 재업로드 필요를 응답으로 안내하고, NUL이나 미지원 형식 같은 영구 오류는 재시도를 거부한다 (research 08 §6.2).
- [ ] B5 `retry_count`가 상한을 넘으면 재시도를 거부해 독성 문서의 무한 재시도를 막는다 (research 08 §6.1).
- [ ] B6 재시도 라우터 엔드포인트(`POST /documents/{id}/retry`)를 추가해 위 서비스 메서드를 호출한다.

## 프런트엔드 (프로토타입 우선)
> 실 기능은 디자인 프로토타입을 먼저 만들고 개발자 컨펌을 받은 뒤에만 구현한다.
- [ ] C1 `web/app/design/retry/page.tsx`에 재시도 UI 디자인 프로토타입을 정적 더미로 만든다 (실 API 배선 없이 화면만).
- [ ] C2 개발자 컨펌을 받는다. 컨펌 전에는 아래 C3 이후 실 기능 구현을 시작하지 않는다.
- [ ] C3 (컨펌 후) 상태가 `failed`인 문서 카드와 목록 행에 "재시도" 버튼을 노출한다 (document-frontend §3).
- [ ] C4 (컨펌 후) 재시도 호출 훅을 만들어 낙관적으로 상태를 `processing`으로 바꾸고 진행 폴링을 재개한다 (document-frontend §3).
- [ ] C5 (컨펌 후) 응답이 재업로드 필요이면 재시도 대신 재업로드를 안내하도록 UI를 분기한다 (research 08 §6.2).

## 검증
