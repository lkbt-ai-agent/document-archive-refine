# 검색 & RAG

## 1. 기능 요구사항
- 키워드 검색 / 의미 검색 / RAG 질의응답.
- 키워드는 PGroonga, 의미는 pgvector 확장에 의존한다. 대표 시나리오: "작년 내 연봉이 얼마였지?".

## 2. 검색 종류
- 키워드·의미는 검색 UI에서 고르는 retrieval 모드로 결과 리스트를 반환한다(기본값 의미). RAG는 별도 "질문" 동작으로 답변을 반환한다.
- 키워드 검색 (희소 검색, sparse retrieval)
  - 희소 검색: 텍스트를 어휘 크기의 희소 벡터(대부분 0이고 등장 토큰 자리에만 값)로 보고 토큰을 글자 그대로 매칭한다. 정확한 단어·이름·코드에 강하지만 동의어·의역은 못 잡는다.
  - 대상: 청크 본문(`document_chunks.content`), 청크 단위.
  - 청크 텍스트를 한국어 키워드(n-gram 토큰)로 매칭하고, 매칭 청크와 그 소속 문서를 리스트로 반환한다.
- 의미 검색 (밀집 검색, dense retrieval)
  - 밀집 검색: 텍스트를 의미를 담은 밀집 벡터(임베딩)로 바꿔 벡터 유사도로 매칭한다. 동의어·의역·문맥에 강하지만 드문 정확어는 놓칠 수 있다.
  - 대상: 청크(`document_chunks`), 청크 단위.
  - 질문을 임베딩해 청크 코사인 유사도로 상위 k개를 매칭하고, 매칭 청크와 그 소속 문서를 리스트로 반환한다.
- RAG
  - 검색 단계는 의미 검색(청크)만 사용한다.
  - 검색된 청크로 컨텍스트를 만들어 답변+출처를 생성한다.

## 3. 자연어 질의 해석
- 검색 종류는 자동 분류하지 않는다. 사용자 진입점으로 갈린다.
  - 키워드/의미: 검색 UI의 모드 선택(기본 의미).
  - RAG: 별도 "질문" 동작.
- 이 단계는 타입을 고르는 게 아니라, 입력 질의에서 재작성 질의·키워드·기간·폴더를 구조화해 추출한다.
- 상대적 날짜("작년" 등)는 요청 시각을 기준으로 절대 범위로 환산한다.
- "내", "나" 등의 단어는 항상 소유자 스코프로 강제한다.

## 4. 검색·RAG 흐름
- 종류마다 시작과 끝이 다르다.
- 키워드 검색
  1. 질의 입력(사용자 키워드)
  2. 청크 본문(`document_chunks.content`) 키워드 매칭
  3. 매칭 청크·소속 문서 리스트 반환 (끝)
- 의미 검색
  1. 질의 입력
  2. 질문 임베딩
  3. 청크(`document_chunks`) 코사인 유사도 검색
  4. 상위 k개 청크·소속 문서 리스트 반환 (끝)
- RAG
  1. 자연어 질문 입력
  2. 질의 해석(§3)으로 재작성·필터 추출
  3. 의미 검색으로 상위 k개 후보 청크 확보
  4. 컨텍스트 조립(청크 본문 + 제목·날짜·폴더·청크 식별자, 인용 번호↔청크 매핑 저장)
  5. 인용 강제 생성
  6. 답변+출처 반환 (끝)

## 5. 리랭킹 (MVP 제외)
- MVP 에서는 고려하지 않는다.
- 상위 결과를 재정렬해 정밀도를 높인다.

## 6. 인용·환각 억제
- 시스템 규칙: 제공된 문서에만 근거하고, 없으면 "찾을 수 없습니다"로 답한다.
- 문장마다 인용 번호를 강제한다.
- 주입 순서: 시스템 규칙 → 컨텍스트 → 질문(마지막).

## 7. 검색 평가 게이트
- 한국어 골든셋(쿼리→정답 문서)으로 Recall@5/@20을 측정한다.
- MVP: 키워드·의미 검색별 Recall을 비교하고, RAG 답변의 인용 존재를 이진 체크한다.
- MVP 이후: 리랭크(§5) 도입 시 비교 항목에 추가한다.
- CI(지속적 통합, Continuous Integration) 파이프라인에서 결정적으로 돌린다.

## 8. 도메인 규칙
- 모든 검색·질의는 소유자 스코프를 강제한다.
- 검색 UI 에서 검색 모드를 선택할 수 있어야 한다.
- 검색은 결과 리스트(retrieval), RAG 질문은 답변 생성으로 역할을 분리한다.
